# 刻意不做的東西

2026-08-08 建立。

這份文件回答一個問題：**哪些是還沒做完，哪些是決定不做。**

散在 `known-risks.md`、`proposals/`、SDD §9、`DANGLING_THRESHOLDS` 和
`decisions.md` 作廢條目裡的東西，分不出這個區別——它只存在於當時做決定的人
腦裡。這份清單把它外部化。

**每一項都有恢復觸發條件。凍結不是放棄，是「現在不做，而且知道什麼時候
該重新考慮」。**

## F1：雲端模型配置（Gemini）

**狀態**：已實作、已驗證品質更好、**刻意不啟用**。

**為什麼停**：20 RPD 的額度限制下，單支影片需要 3 天。與「批次處理大量影片」

**代價**（已知並接受）：

| | Gemini | 本地 |
|---|---|---|
| 溯源通過率 | 0.986 | 0.838 |
| `slide_text` CER | 4.9%（最佳模型） | 最差到 37.8% |

程式碼保留在 `stages/providers.py`，未刪除。

**恢復觸發條件**：某一批素材的本地 CER 高到 chunk 無法使用時，
針對那一批單次啟用。不改回預設。

## F2：追 §5.2 的 0.95 到綠燈

**狀態**：**該數字的語意已修正，不再是驗收目標。**

**為什麼停**：0.95 從 §5.4 的「5% 容忍度」來，而那個 5% 沒有依據。
更嚴重的是同一個數字承載三種語意：§5.4 的 per-video 閘門、
§5.2 的全域驗收門檻、R27 算的四支合計。

SDD §5.2 自己對 `slide_text` 的 CER 寫過「**不憑感覺訂一個數字**」——
這條紀律沒有被套用在 0.95 上。

**處置**：**已落地**（票 03）。拆成
`PROVENANCE_PER_VIDEO_GATE = 0.95`（真的擋，值未動）與
`provenance_rate_overall`（只記錄，列在 `thresholds.OBSERVED_ONLY`，
規約測試會擋它被誤登記成驗收門檻）。

逐支的量測**帶成因分解**寫進 `out/provenance.jsonl`：
`wrong_source`／`depends_on_correction`／`unresolved`。
只給一個比率等於沒說——R27 的 27 筆未通過裡，17 筆的病根不在內容品質。

**恢復觸發條件**：當有了「產出好不好用」的評測（SPEC D-J），
若實測顯示某個溯源水準以下可用性明顯下降，**用那個實測值**訂門檻。
不是回頭撿 0.95。

> **2026-08-08 進度（票 12／R34）**：評測有雛形了——檢索導向的 R@k／MRR，
> 完全機械化不用 LLM 當裁判。同一組題上 weft R@1 1.000 vs naive 固定視窗
> 0.812（差 +0.188），**指標有區辨力**。
>
> **但還不能拿來訂門檻**：16 題、69 chunk、兩支影片，而且排除規則恰好
> 排掉了 weft 唯一失敗的那題。票 11 的 26 支課程（≈800 chunk）跑完之後重量。
>
> 附帶記錄一個錯誤：我第一版量到的差距只有 +0.055，並據此寫下
> 「這個指標沒有區辨力、F2 的觸發條件仍未滿足」。**那是我的對照組寫錯**
> （gold 對映用「有重疊就算」，讓對照組在更容易的題目上計分）。
> R23 的教訓第二次發生：**對照組出錯時會偽裝成「訊號不準」**。

## F4：公開語料（SlideSpeech / M3AV / SlideAVSR）

**狀態**：**語種未證實，暫不採用。**

**為什麼停**：SlideSpeech 官網（CC BY-SA 4.0）沒有語言欄位，

拿英文語料的結論套中文素材，與 §1.3 把單支影片推廣成系列通則，
是同一種推廣錯誤。

**恢復觸發條件**：下載後確認含足量中文內容。屆時可作為
**跨語料驗證**（方法在乾淨資料上會不會動），**仍不可用於訂本專案的門檻**。

## F5：階層式分段（TreeSeg）

**狀態**：使用者有此構想、文獻支持、**未評估**。

**為什麼停**：使用者原話——「可能會做得超級複雜」。這個判斷是對的：
它是在單層分段還沒做出來之前就疊第二層。

**但它不是壞主意**：長逐字稿（機器人學課程 30–90 分鐘）的層級關係，
單層 chunk 會整個丟掉；而 Obsidian 本身就是階層加網狀結構。
使用者的動機——「不是每一段內容都同樣重要，讓模型在該注意的地方注意」——
正是 TreeSeg 要解的問題。

**恢復觸發條件**：單層語意分段（票 #8）跑完並驗證有效之後。
探索票 #14 已建立，不在收尾範圍。

## F10：yt-dlp 的 JS challenge solver（`--remote-components ejs:github`）

**狀態**：**不啟用。** 影響已量測，代價未量測。

**為什麼停**：yt-dlp 2026.07 之後，YouTube 的部分格式需要解 JS challenge。
機器上有 node（v22）沒有 deno，已把 `s0.js_runtimes` 指定為 node，
消掉「No supported JavaScript runtime」那個警告。但**實測格式數與解析度
完全沒變**：

| | 格式數 | 視訊 | 最高 |
|---|---|---|---|
| 預設（無 runtime） | 16 | 9 | 720p |
| 指定 node | 16 | 9 | 720p |

要再往上得開 `--remote-components ejs:github`——那會在**執行期從 GitHub
下載並執行腳本**。這是供應鏈層級的取捨，不由實作者單方面決定。

**未量測的代價**：已下載的三支全是 720p，而 R21／R22 的 `slide_text` CER
（最佳 12.9%）也全是在 720p 上量的。**1080p 會不會讓 CER 下降，沒有量過**，
甚至「這些影片有沒有 1080p」都不知道——那要先解 challenge 才看得到。

**恢復觸發條件**：若 `slide_text` 的品質被確認是瓶頸（票 10 的逐段 prompt
重測若仍無改善），先量「同一張投影片在 720p 與 1080p 下的 CER 差多少」，
再決定要不要為此接受遠端元件。**不要為了消掉一個警告就開它。**

### 2026-09-01 更新：問題升級成「完全下載不了」，但**升級 yt-dlp 就解了**

整批跑機器人學播放清單時，26 支有 **23 支 `HTTP Error 403: Forbidden`**。

診斷過程（每一步都排除一個候選）：

| 測試 | 結果 |
|---|---|
| 沙箱內 `weft prepare` | ✗ 403 |
| 沙箱外 `yt-dlp --simulate`（只抓 metadata）| ✓ 成功 ← **這一步讓我誤判成「沙箱問題」** |
| 沙箱外**真的下載** | ✗ 403（媒體網址 `googlevideo.com`）|
| `player_client=web / web_safari / mweb` | ✗ Requested format is not available |
| `player_client=tv` | ✗ The page needs to be reloaded |
| **yt-dlp 2026.07.04 → 2026.08.19** | ✓ **成功** |

**根因**：舊版用 `ANDROID_VR` client，YouTube 把它的媒體網址 403 掉了。
其他 client 全都要 PO token（就是本條凍結的那個 JS challenge）。
新版改用 `visionos` client，**繞過去了，不需要開 `--remote-components`**。

> **這條凍結因此仍然成立**，而且理由更強：**先升 yt-dlp，不要先開遠端元件。**

**格式清單變了**：新版沒有合併好的格式（舊的 itag 18），只有分開的
video-only + audio-only，要 ffmpeg 合併。現行的
`bestvideo[height<=1080]+bestaudio/best[height<=1080]` 本來就走合併路徑，
**不用改**。最高仍是 720p，與上表一致。

> **給下一個撞到 403 的人**：
> **先 `pip install -U yt-dlp`。** YouTube 每隔幾週就改一次，
> 而症狀是「metadata 拿得到、媒體下載 403」——很容易被誤判成網路或環境問題
> （我就誤判了一次，還把它連到別的事故上）。

## F11：分段邊界的容忍窗要訂多少（2026-08-09，R37）

**狀態**：`BOUNDARY_TOLERANCE_SEC = 2.0` **不動**。分段**不設** F1 門檻。

R37 量到：容忍窗的有效性取決於**它 × 刀數密度**。同一個窗在換頁偵測上
健康（10 刀 / 14 分鐘 → 覆蓋 5%），在分段上失效（30–57 刀 → ±20s 覆蓋
80–95%、±30s 覆蓋 100%）。全域改小會把好的那一邊一起弄壞。

R30／R37 報告裡用的 ±10s **是看了覆蓋率之後選的**，不是事先訂的。
它比 ±20s 有區辨力，但「多少才對」沒有獨立依據，而依覆蓋率反推
會讓門檻隨刀數浮動——那不是門檻，是後見之明。

**要訂得先回答一個產品問題**：使用者在 vault 裡點開一個 chunk，
它的起點差幾秒還算「切對地方」？那取決於怎麼用，不是實作能決定的。

已做的替代處置：`MAX_TOLERANCE_COVERAGE = 0.80`——**檢查門檻本身還
成不成立**。覆蓋率超過它就紅，訊息明寫「不要調低 F1 門檻」。

**恢復觸發條件**：
1. 票 13 的後半做完（chunk 真的進 vault、使用者實際查過）——
   那時「差幾秒還算對」會有真實答案；
2. 或分段方法要換掉時——換方法必須有可信的比較依據，
   而 ±20s 那組數字已知不可用。

## F12：`chunk.id` 的形狀（2026-08-09，票 13）

**狀態**：維持 `<video_id>#<段序號>#b<塊序號>`，**位置編號，不改**。

它有一個真的缺陷：重跑後同一個 id 可以指到不同的內容與時間範圍
（D32 的同一個根源，見 `experiments/r38_chunk_contract_audit/REPORT.md` §2）。

不改的理由是**沒有明顯較好的替代**，而且選擇取決於下游：

| 方案 | 代價 |
|---|---|
| 內容雜湊 | 改一個字就變成新筆記，vault 累積孤兒 |
| `(video_id, t_start)` | 微調分段就漂移，但漂移量小且有語意 |
| 維持位置編號 | **穩定但會說謊**——id 沒變，內容變了 |

**已做的替代處置**：`ChunkMetadata.content_sha`，由 §5.3 規則 8 核對。
不解決識別問題，但**讓「內容變了」在下游看得見**。
給 vault 的建議寫在 R38 §2：用 `(video_id, t_start)` 當識別，
`content_sha` 當變更偵測，**不要用 `id`**。

**恢復觸發條件**：vault 側的 ingest 決定用什麼當筆記識別之後。
那時這裡要跟著給一個穩定欄位，而不是讓下游自己組。
