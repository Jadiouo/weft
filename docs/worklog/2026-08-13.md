## 1. 決定一（D34）：閘門擋的不是壞內容，是好內容

報告給使用者時我先畫錯了一張表，當場更正：**未通過的 block 本來就不會進
`chunks.jsonl`**（S6 逐塊過濾，§5.4 第一層）。所以 per-video 閘門是
**第二層**，它擋的是「這支影片整體不太可靠」，代價是連已驗證的內容
一起丟。

實測：**被擋的四支裡有 218 個已驗證 block 陪葬，而留下的只有 135 個。**

原閘門的理由仍部分成立——低通過率代表檢查器在該素材上吃力
（R42 實測 STEM 上具名實體檢查空轉、相似度門檻只有 0.05）——
**問題不在理由錯，在於處置是全有全無**。

### 做法

`ChunkMetadata` 加 `video_pass_rate`，把信任門檻的決定推遲到
票 13 後半有依據時。`needs_review` 從閘門降為標記。

**先改規格再動程式**：SDD §5.2／§5.4 更新，`decisions.md` 記 D34。

實測結果：`chunks.jsonl` **135 → 354 筆**，八支全收。

### 三處需要誠實處理的

1. **`video_pass_rate` 做成可為 `None`。** 溯源沒跑時填 1.0 會讓
   「沒檢查過」看起來像「完美通過」——那比缺值更糟。
2. **那條編碼舊行為的測試改寫而非刪除。** 它原本守的問題
   （上一版 chunk 留在輸出裡）沒有消失，只是處置從「移除」變成「覆寫」。
3. **D34 初稿寫「`PROVENANCE_PER_VIDEO_GATE` 要移出
   `ACCEPTANCE_THRESHOLDS`」，那是搶先下的結論。** 它仍被兩處斷言
   強制執行，只是角色從閘門變成標記邊界。**D30 的規約守衛判斷是對的，
   我錯了**，已更正。

### 順帶抓到兩件

- 一條 live 測試斷言 `zIglvjoU9vo` 通過率 ≥ 0.95，**而實測 0.947**——
  手動跑會紅，被 marker 遮著。改為釘住實測值。

## 2. 溫度做成設定——同一類 bug 的第六次

要測 `temperature=0.0` 就得先讓它可設定。做的時候發現它原本
**寫死在 `providers.generate()` 的預設值**（0.2）——沒有人選過它。

關鍵是：**它必須進 S4c 的逐段冪等鍵**，否則改了會靜靜命中舊快取、
量出「改了沒效果」。

| | 漏掉的東西 |
|---|---|
| D20／D22 | 早期的階段參數 |
| D30 | `prompt_version`（未錨定的字串替換 bump 錯類別）|
| D32 | `segment_id` 的位置性 |
| α（8/9）| `DEPTH_ALPHA` 是模組常數，不在 `cfg.s3` 裡 |
| **溫度** | 寫死在 `generate()` 的預設值 |

**第六次，所以在做出來的當下就留了 6 條測試**，含兩條容易漏的：
逐段快取才是真正會咬人的那一層；「進了鍵卻沒傳給模型」——
鍵是對的而行為沒變，那更難發現。

## 3. `temperature=0.0` 沒有用——而我第一次量錯了（R45）

| 設定 | n | 樣本（總產出字數）| CV | 全距 |
|---|---|---|---|---|
| `temperature=0.2` | 5 | 600 / 722 / 818 / 1041 / 1386 | 0.34 | 2.31× |
| `temperature=0.0` | 3 | 551 / 758 / 1253 | **0.42** | **2.27×** |

**沒有降低變異。** 已退回 0.2；欄位與冪等鍵保留，
下一個人要試 `top_k`／`top_p` 時機制已經在了。
**「兩邊各 3 個樣本」的規則不變。**

### 第一次量出「三次完全相同」，是假的

```
T=0.0 run1: 17 block、1041 字  （記錄的溫度 {None}）
T=0.0 run2: 17 block、1041 字  （記錄的溫度 {None}）
T=0.0 run3: 17 block、1041 字  （記錄的溫度 {None}）
```

看起來就是「T=0 讓它變確定性了」。**實際上 `ollama` 沒開**，
三次呼叫全部 `Connection refused`，而腳本用了 `>/dev/null 2>&1`。
`08_video.json` 沒被更新，三次讀到**同一份舊檔**——
1041 字正是 R44 裡 `temperature=0.2` 的第五個樣本。

**抓到它的是 `記錄的溫度 {None}`。** 那個欄位是同一批工作順手加的
（為了進冪等鍵），新跑的結果應該要有值。追下去才發現
`07_understanding` 是空的。

> 那個欄位加進去的目的是冪等鍵，**它在自己第一次派上用場時，
> 抓到的是我自己的錯誤**。而假結果的方向剛好是我預期的——
> 那是最難發現的一種。

**同一天第二次踩 `>/dev/null` 吞錯誤**（8/9 那次是
`weft prepare --video` 的語法錯誤）。修法記在 known-risks R37：

> **量測腳本要驗證「它真的做了那件事」的正面訊號，
> 不是只看有沒有錯誤。**

實作：檢查 `10/10 個 segment` 出現、檢查快取檔真的寫出來、失敗 `exit 1`。

## 4. 票 15：前提是錯的，實際缺陷在別的地方

票 15 原本寫「`series_id` 沒有流到 chunk，兩個同名欄位是不同的東西」。
**查完發現那條鏈本來就是通的**——八支素材是 `None` 只因為當初都用
單支 video_id 抓的，**那時 `None` 是正確的值**。

真的缺陷：**回填不會發生。** 一支影片先以單支 id 抓過、之後再用
playlist 跑時，S0 是「已滿足」的，蓋 `series_id` 那段整段跳過。
而重抓影片沒有理由（檔案就在那）——**這不是快取失效問題，
是旁路資訊沒有回填**。

已修，6 條測試。其中一條守的是：**單支來源時 `None` 是正確的**——
沒有它，「補上系列資訊」很容易被實作成從標題猜，而
「古典醫學之人體設計系列-**27**胰腺」裡的 27 是不是集數，
換一個系列就不一定了（v0.2／v0.4 兩次栽在這類推廣）。
