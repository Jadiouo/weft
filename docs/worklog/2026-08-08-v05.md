## 主要結果

### 主幹換成逐字稿（票 07 → 08）

**先量再做。** 提案 §6 的三個方向到這次為止一個都沒量測過。

| 方案 | 保留集 F1 | 召回 |
|---|---|---|
| 現行：投影片切換驅動 | 0.439 | 0.60 |
| SPEC D-B 的方向 2 | 0.471–0.529 | 0.53–0.60 |
| **純語意** | **0.667** | **0.93** |

**方向 2 輸的是結構問題不是調參問題**：它只能是投影片切換的**子集**，
永遠找不到它沒找到的邊界，因此繼承 0.50／0.60 的召回上限。
而漏掉的正是「講者對著同一張圖講完兩件事」那一類。

實作後的下游影響：

| | v0.4 | v0.5 |
|---|---|---|
| 溯源合計 | 135/155 = 0.871 | **152/163 = 0.933** |
| 被閘門擋下 | 4/4 | 2/4 |
| `chunks.jsonl` | **0** | **69** |
| 段落中位長度 | 13–14 秒 | 44–53 秒 |

**ngram 與 sbert 分不出高下，我沒假裝分得出來。** 掃 `BLOCK_CHARS`
發現排名隨它翻（ngram 在 0.353–0.762 之間跳）。用「調校集選參數、
只報保留集」的協定，兩者都是 0.667。選 ngram 不是因為比較準，
是因為不需要模型／GPU／下載。

### 逐段 prompt 有效，R20 的結論被推翻（票 10）

| 組 | 術語 | CER |
|---|---|---|
| 無 prompt | 6/20 | 0.143 |
| **全域** 200 字（R20 的做法） | 5/20 | 0.132 |
| **逐段**詞序列 | **9/20** | **0.113** |
| **逐段**經文段落 | **9/20** | 0.115 |

差別不在插入點，在**粒度**。全域 prompt 把整支影片的術語混在一起餵給
每一段——雜訊不是提示，實測甚至比不給還差一個術語。
**格式沒有差別**，贏的是粒度。

CER 相對改善 14.4%，DocWhisper 報的是 WER 14.3%。

## 六次「我做壞了」

### 1. D32：`segment_id` 是位置編號，而冪等鍵只認它

換掉分段方式後第一次重跑，數字**崩盤**（cxrq 0.929 → 0.071）。
查出 `#010` 現在是 564–593 秒，但它的 `understanding` 講的是 72–98 秒的內容。

§4.7 的冪等鍵是 `segment_id + prompt_version + model`，而 `segment_id`
是位置編號。換一種分段方式，同一個編號涵蓋完全不同的內容，
**舊快取照樣命中**。

> **每一項機械檢查都是綠的。** 欄位都在、格式都對、§5.3 不變量全過，
> 只是講的是別的地方的事。

**這是同一個錯誤的第四次**（D20 圖片錯位／D22 衍生狀態／D30 prompt 版本／
D32 分段）。共同點：輸出「錯位」不會自己報錯。

### 2. 量測腳本寫了生產資料

比較新舊分段的腳本直接呼叫 `s3_align`——而**它會寫
`work/06_segments.json`**。同一輪 `weft prepare` 的 target 是位置引數，
我用 `--video` 呼叫四次全部失敗，而 `>/dev/null 2>&1` 把錯誤吃掉。

兩件疊起來讓資料變成「兩支新分段、兩支舊分段」，
我差點把那個混合狀態的數字當成結論。

### 3. 量測沒對齊字集

票 10 第一版量出「無 prompt」組是 0/20、CER 0.415，與 R20 報的差很遠。
原因是 R17 的輸出是**簡體**，而我的量測沒轉繁。
**那不是「無 prompt 有多差」，是我沒對齊字集。**
R20 的 `measure.py` 第一行就寫了要轉繁，我重寫時弄丟了。

### 4. `depends_on_correction` 只比相似度（code-review 抓到）

`check_block` 有三種未通過成因。一個因「來源長度僅 8%」失敗的 block，
對校正後版本的相似度照樣能高過門檻，於是被蓋上「靠校正才對得上」的章
——**那是一句假話寫進人工複核文件**。而且「圖表描述」的門檻是 0.0，
該寫法對它數學上不可能成立。

### 5. `chunks.jsonl` 重複了 4.7 倍（code-review 抓到）

我修了 debug 檔的重複附加，卻沒修**產品輸出**。實測 428 行、
相異 id 只有 91 個、最高重複 5 次。而且**既有測試把這個缺陷寫成了
期望行為**——`test_chunks_jsonl_appends_across_videos` 名字說 across
videos，內容卻是同一份 IR 寫兩次斷言行數變兩倍。

### 6. 對照組寫錯，讓我下了反的結論（總體 code-review 抓到）

票 12 的對照組 gold 對映用「**有 >0 秒重疊就算命中**」。那讓對照組在
一個**更容易的題目**上計分：58 個 naive chunk 拿到 gold 資格，其中
**21% 的重疊不到自身時長的四分之一**——一個內容 75% 不相干的視窗
被算成命中。候選池又只有 40 個（weft 69），隨機命中率高 1.7 倍。

於是量到的差距只有 R@1 0.055，而我據此寫下**「這個指標沒有區辨力」**，
並把它寫進 known-risks R25 與「FROZEN F2 的觸發條件仍未滿足」。

修對之後（門檻改為 naive chunk 自身時長的 ≥50%、兩邊同一組題）
差距是 **+0.188**——**3.4 倍**。

> **R23 的教訓第二次發生**：對照組出錯時不會長得像「對照組錯了」，
> 會長得像「這個訊號沒那麼準」。
>
> 唯一抓到它的方式是**去看對照組的 gold 集到底長什麼樣**。
> 平均分永遠不會告訴你這件事。

同一輪還抓到 R24 的簡體字統計是錯的（27.5% → 10.1%，`s2tw` 把異體字
算成簡體），而且我提的修法會把講者的姓 `游朱義` 改成 `遊朱義`。

## 方法論：這次再驗證的東西

- **先量再做是有代價的，但代價比反過來低。** 票 07 花了一輪量測，
  結果推翻了規格自己寫的方向 2——那個方向若直接實作，會做出一個
  召回上限 0.60 的東西，而且看起來很合理。
- **對照組是必需品，但寫錯的對照組比沒有更糟。** 票 12 的第一版對照組
  讓我下了與事實相反的結論，而且那個結論已經寫進 known-risks 與 FROZEN
  的引用鏈。**沒有對照組的漂亮數字什麼都不是；寫錯的對照組會產生
  看起來很謙虛、實際上是假的悲觀結論。**
- **驗證對照組的方式是去看它的 gold 集，不是看它的分數。**
- **輸出「錯位」與「變少」都不會自己報錯**（D32、D31）。而且分母變小
  還會讓比率型指標**更好看**。
- **量測腳本不該碰生產路徑的寫檔函式。**
- **把輸出丟到 `/dev/null` 之前要先確認指令本身是對的。**
