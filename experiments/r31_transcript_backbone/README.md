## 2. 改了什麼

`Segment` 不再由 `Slide` 切換決定。S3 的職責從「對齊」變成「分段」：

- **TextTiling**（Hearst 1997）在逐字稿上找話題邊界，
  表示用**字元 n-gram**（不需斷詞、不需模型、不需 GPU）
- 斷點門檻用文獻的 `mean − std/2`，**不自訂**，也不把答案數量餵給它
- **投影片切換完全不參與決定切在哪裡**，降級為「這一段螢幕上是哪一張」
  的註記（取時間重疊最久的；重疊為零就是 `None`）

票 07 已經量過，方向 2（切換降為候選 + 語意佐證）輸的是結構問題：
過濾器只能是切換的子集，**永遠找不到它沒找到的邊界**。

## 3. 中途踩到的坑：`segment_id` 是位置編號，而冪等鍵只認它

第一次重跑的數字是**崩盤**的：

```
cxrqHABhWOU  0.929 → 0.071
2FjApOVIbUs  0.900 → 0.156
合計         0.871 → 0.626
```

查下去發現 `#010` 這一段現在是 **564–593 秒**，但它的 `understanding`
講的是「胰腺體是長這個樣子，這裡面有非常多的胰管和胰小葉」——
那是 **72–98 秒**的內容。

§4.7 的冪等鍵是 `segment_id + prompt_version + model`，而 `segment_id`
是**位置編號**（`#010`）。換一種分段方式之後，同一個編號涵蓋完全不同的
時間範圍，**舊快取照樣命中**。

> **每一項機械檢查都是綠的。** 每個欄位都在、格式都對、
> 不變量全過——只是講的是別的地方的事。
> 這與 D20 的圖片錯位、D31 的內容掉 87%、D22 的 rehydrate 回傳空的
> 是同一類：**輸出「錯位」不會自己報錯**。

修法：`Understanding.input_fingerprint` = 該段的
`t_start | t_end | slide_ref | transcript_raw` 的雜湊，納入冪等鍵。
**沒有指紋的舊快取一律不命中**——讓它命中等於相信一個無法驗證的假設，
而那個假設正好就是出事的那個。

修完重跑就是 §1 的數字。

## 4. 另一個過程中的教訓：量測腳本寫了生產資料

我第一次比較新舊分段時，量測腳本直接呼叫 `s3_align`——而它會
**把結果寫進 `work/06_segments.json`**。於是那次量測順手改掉了兩支影片的
分段，而我以為它們是「沒重跑」。

同一輪還有：`weft prepare` 沒有 `--video` 參數（是位置引數），
我四次呼叫全部失敗，而 `>/dev/null 2>&1` 把錯誤吃掉了。

兩件事疊在一起，資料狀態變成「兩支新分段、兩支舊分段」，
而我差點把那個混合狀態的數字當成結論。

**教訓**：量測用的程式碼不該碰生產路徑的寫檔函式；
把輸出丟到 `/dev/null` 之前要先確認指令本身是對的。
