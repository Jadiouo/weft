# R28（票 01）：溯源基準改回 `transcript_raw`

2026-08-08。SPEC v0.5 的 D-C。

**結果：四支既有影片的通過率完全沒有變動（135/155 = 0.871），
`depends_on_correction` 一筆都沒有。**

這個零是真的，但**不能當成「這個修正沒必要」**——原因見 §3。

---

## 1. 改了什麼

```python
# 之前
transcript = seg.transcript_corrected or seg.transcript_raw
# 之後
transcript = seg.transcript_raw
```

S4b 用投影片文字校正逐字稿的同音錯字（§4.7b），再拿校正後的逐字稿去驗證
同樣來自投影片的內容——**用來源 A 驗證來源 A**。投影片的資訊被寫進逐字稿，
繞一圈回來當成獨立佐證；模型若把投影片讀錯，那個錯誤會被溯源檢查蓋章認證。

§5.4 已警告過獨立性下降，但**實作比警告描述的更嚴重一級**：
警告說的是「來源由 VLM 產生」，實際發生的是「兩個來源已經混在一起」。

`transcript_raw` 一旦寫入即為唯讀（§5.3 不變量 9），是這條管線裡
唯一不會被任何模型碰過的東西。

搭配新增 `depends_on_correction`：未通過、但對**校正後**的逐字稿對得上的，
標記出來。**不改判為通過**——術語校正的 precision 門檻是 0.90，沒有餘裕
（§5.2），拿一個 90% 準的東西當「有出處」的依據，等於把 10% 的模型判讀
寫成事實。

## 3. 為什麼是零——這批素材測不到這件事

**四支影片全部使用手動字幕**（`manual_caption`），不是 Whisper。

| 影片 | 逐字稿來源 | 有校正的 cue |
|---|---|---|
| zIglvjoU9vo | manual_caption | 24 / 925 |
| C_CFyilE-ks | manual_caption | 0 / 429 |
| cxrqHABhWOU | manual_caption | 1 / 322 |
| 2FjApOVIbUs | manual_caption | 1 / 588 |

而且校正都是**長段落裡的單字替換**，bigram containment 幾乎不動：

```
zIgl/011  '憍梵钵提'→'憍梵波提'   對 raw 0.297  對 corrected 0.328
zIgl/019  '經'→'經文'             對 raw 0.727  對 corrected 0.740
zIgl/032  '四月陰靈'→'四月陰霊'   對 raw 0.348  對 corrected 0.341
cxrq/011  '胰臟'→'胰腺'           對 raw 0.373  對 corrected 0.373
```

沒有任何一筆跨過型別門檻。

**R18 量過 Whisper 輸出的同音錯字才是大宗**，而這四支一支都沒用到
Whisper 路徑。也就是說：**這個修正結構上是對的，但這批素材無法展示它。**
真正會踩到的是票 09（無投影片路徑，必然走 Whisper）與票 11 的三組素材。

## 4. 因此用單元測試證明它會觸發

「量出來是零」與「這段程式碼從來沒被執行過」在報表上長得一模一樣——
這個 repo 為此付過代價（§5.2 的門檻有 4 項只 assert 常數值）。

`tests/test_unit_provenance.py` 新增四條，構造一個**等長同音替換**
（`時運` → `識蘊`，R18 實測的典型形態）：

| 測試 | 斷言 |
|---|---|
| `test_baseline_is_raw_not_corrected` | 校正後才對得上的內容**不通過** |
| `test_correction_dependent_block_is_flagged_not_silent` | 標記 + 理由 + 彙總都在 |
| `test_content_matching_raw_is_untouched` | 本來就對得上的不受影響 |
| `test_no_correction_means_no_flag` | 沒有校正時不得標記 |

第三條存在的理由：沒有它，前兩條可以靠「把所有東西都判成未通過」通過。

**寫測試時發現的事**：這四條原本用 `白話解說`（門檻 0.10）寫，
結果單一術語的差異推不動它，`識蘊進入的時機` 對 raw 也有 0.143 > 0.10。
改用 `經文原文`（門檻 0.60）才測得到——這與 R12 的量測一致：
containment 只對經文原文有鑑別力（分離 7.50x），白話解說是 1.14x。
**用一個本來就擋不住東西的型別去測「基準換了會怎樣」，測不到東西。**

## 5. code-review 抓到的實作錯誤（已修）

**`depends_on_correction` 原本只比相似度，那會說謊。**

`check_block` 有三種未通過的成因（相似度、來源長度比、具名實體）。
一個因「來源長度僅 8%」而失敗的 block，它對校正後版本的相似度照樣可以
高過門檻——於是被蓋上「靠校正才對得上」的章，而實際上換成校正後版本
重跑它仍然不會過。**那是一句假話寫進 §5.6 的人工複核文件。**

而且 `圖表描述` 的相似度門檻是 0.0，`sim >= 0.0 > verdict.similarity`
**數學上不可能成立**——那個型別的標記形同不存在，
卻正是票 01 說要讓它看得見的東西。

改為**把整個 `check_block` 對校正後的逐字稿再跑一次**，比對 status。

## 6. 順手修掉的三個缺陷

1. **`unverified.jsonl` 是純附加模式**，重跑一次就把同一批未通過再寫一遍。
   實測跑兩次後檔案裡有 36 筆，實際只有 18 筆。§5.6 的人工複核從這個檔案
   數「有幾筆要看」會數成兩倍，而且新舊程式碼的紀錄混在一起看不出來。
   改為**同一支影片取代舊紀錄**，別支的保留。
2. **人工複核文件只顯示校正後的逐字稿**。這份文件要回答的問題之一正是
   「這段內容是不是靠校正才成立的」，把校正後的當成唯一的逐字稿看，
   那個問題就問不出來。改為原始版本為主、校正後的另附（且只在真的不同時）。
   附帶：原本要寫「校正 N 筆」，但 `segment.corrections` 存的是**提案**，
   `apply_corrections` 只套用 `from_text` 真的出現在 cue 裡的那些。
   在複核文件裡寫一個比實際多的數字，等於捏造一個讓人據以判斷的事實。
   改為不寫筆數。
3. **`chunks.jsonl` 有一模一樣的問題，而且更嚴重**——那是要進向量庫的
   **產品輸出**。實測 428 行、相異 `id` 只有 91 個、最高重複 **5 次**。
   重複的 chunk 會讓同一段內容在檢索結果裡佔掉數個名額。
   `Chunk.id` 是穩定的（segment + block index），重複可辨識，
   但沒有任何一步在辨識它。

   更值得記的是：**既有測試把這個缺陷寫成了期望行為**。
   `test_chunks_jsonl_appends_across_videos` 的名字說 across videos，
   內容卻是拿同一份 IR 寫兩次、斷言行數變兩倍。已改成真的測跨影片，
   並補上「同一支重跑會取代」。

## 7. 成因分類現在看得見

`wrong_source` 與 `depends_on_correction` 寫回 `ContentBlock`，
因此進得了 `08_video.json`、`unverified.jsonl` 與人工複核文件。

三種未通過的修法完全不同，混在一個 `unverified` 裡等於看不見：

| 成因 | 要修的是 |
|---|---|
| `wrong_source` | S4c 的 prompt（來源型別標錯）|
| `depends_on_correction` | 實質溯到投影片，改標 `slide_ocr` 或人工確認 |
| 兩者皆否 | 才是真的要判內容有沒有問題 |

## 8. 限制

- 四支影片、155 個 block，且**全部是手動字幕**。
- `depends_on_correction` 的判定是「對 corrected 重跑 `check_block` 會過」。
  **實測樣本為零**，只有單元測試的構造案例——它在真實素材上的行為
  要等票 09／11 走到 Whisper 路徑才看得到。
