# R45：`temperature=0.0` 沒有消除變異——而我第一次量錯了

2026-08-13。**兩個結果，一個關於模型，一個關於我自己的量測。**

R44 量到 S4c 的跑次變異有 2.31 倍（CV 0.34），並在 §7 記下
「沒有人試過 `temperature=0.0`——那可能讓整件事消失」。這份報告去試。

---

## 0. 結論先講

| | |
|---|---|
| **T=0.0 沒有降低變異** | CV **0.42** vs T=0.2 的 0.34；全距 2.27 倍 vs 2.31 倍 |
| **所以「兩邊各 3 個樣本」的規則要留著** | R44 §6 的規則不變 |
| **第一次量出「三次完全相同」，是假的** | `ollama` 沒開、`>/dev/null` 吞掉錯誤、讀到舊檔 |
| **抓到它的是剛加的溫度記錄欄位** | 它在自己第一次派上用場時抓到我的錯誤 |
| **已退回 `temperature: 0.2`** | 沒有理由改，而改了會讓所有既有快取失效 |

## 1. 結果

`cxrqHABhWOU`，10 個 segment，清 `07_understanding` 後重跑：

| 設定 | n | 樣本（總產出字數）| 平均 | 標準差 | CV | 全距 |
|---|---|---|---|---|---|---|
| `temperature=0.2` | 5 | 600 / 722 / 818 / 1041 / 1386 | 913 | 310 | **0.34** | 2.31× |
| `temperature=0.0` | 3 | 551 / 758 / 1253 | 854 | 361 | **0.42** | 2.27× |

**沒有改善。** T=0.0 的 CV 甚至略高（但 n=3 對 n=5，這個差距不必當真）。

block 數：T=0.2 是 11/12/12/14/17，T=0.0 是 11/12/13——同樣在動。

## 2. 為什麼 T=0 仍然不確定

**沒有查證，以下是待驗的可能**：

- ollama／llama.cpp 在 `temperature=0` 時仍套用其他取樣參數
  （`top_k`、`top_p`、`repeat_penalty`），我們一個都沒設。
- GPU 浮點運算的非結合性——批次大小、記憶體配置不同會讓 logits 略異，
  而 argmax 在接近的兩個 token 之間會翻。
- S4c 是**批次呼叫**（`batch_segments=3`），批次組成一樣，
  但 KV cache 狀態未必。

**都未驗證。** 要查的話最小的實驗是：同一段內容連呼叫兩次
`providers.generate()`，比對輸出。這裡沒做——因為結論
（「變異還在，規則不變」）不因原因而改變。

## 3. 第一次量錯了，怎麼錯的

第一次跑出來的是：

```
T=0.0 run1: 17 block、1041 字  （記錄的溫度 {None}）
T=0.0 run2: 17 block、1041 字  （記錄的溫度 {None}）
T=0.0 run3: 17 block、1041 字  （記錄的溫度 {None}）
```

**三次完全相同**，看起來就是「T=0 讓它變確定性了」。

實際上：**`ollama` 沒開**。三次呼叫全部 `Connection refused`，
而量測腳本用了 `>/dev/null 2>&1`，錯誤被吞掉。
`08_video.json` 沒有被更新，所以三次讀到的是**同一份舊檔**——
1041 字正是 R44 裡 `temperature=0.2` 的第五個樣本。

### 3.1 抓到它的是什麼

**`記錄的溫度 {None}`。** 那個欄位是這次順手加的
（`Understanding.temperature`，為了進冪等鍵），
新跑的結果應該要有值。追下去才發現 `07_understanding` 是空的——
`_save` 從沒被呼叫，因為模型呼叫全部失敗。

> 那個欄位加進去的目的是冪等鍵，**它在自己第一次派上用場時，
> 抓到的是我自己的錯誤**。

如果沒有它，這份假結果會直接被寫進報告，而且**方向剛好是我預期的**——
那是最難發現的一種錯。

### 3.2 這是同一天的第二次

今天稍早也踩過 `>/dev/null 2>&1` 吞錯誤（`weft prepare --video`
是錯誤語法，target 是位置參數）。

**修法**：量測腳本改成失敗就中止，而且**驗證成功的正面訊號**
而不是只看有沒有錯誤——

```bash
out=$(... understand --video cxrqHABhWOU 2>&1)
if ! grep -q "10/10 個 segment" <<<"$out"; then
  echo "run$run 失敗，中止："; grep -E "ERROR|失敗" <<<"$out" | head -3; exit 1
fi
n=$(ls work/.../07_understanding/*.json | wc -l)   # 快取真的寫出來了嗎
```

「沒有錯誤訊息」不等於「成功了」。**要檢查它真的做了那件事。**

## 4. 處置

- **`temperature` 退回 0.2。** 沒有理由改——它不改善變異，
  而改了會讓所有既有快取失效（那是幾小時的重跑）。
- **`S4Config.temperature` 這個欄位保留**，連同它在冪等鍵裡的位置。
  它現在是可設定的、被記錄的、而且改了會正確地重跑。
  下一個人要試 `top_k`／`top_p` 時，這個機制已經在了。
- **R44 §6 的規則不變**：任何依賴 S4c 輸出的比較，兩邊各至少 3 個樣本。

## 5. 限制

- **只量了一支影片、T=0.0 只有 3 個樣本。**
- 沒有查 T=0 為什麼仍不確定（§2 列了三個未驗證的可能）。
- 沒有試 `top_k=1`——那可能才是真正的貪婪解碼開關。**未評估。**
