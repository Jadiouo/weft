# R29（票 03）：門檻語意拆分——以及一個必須讓使用者知道的後果

2026-08-08。SPEC v0.5 的 D-F。

---

## 1. 修的是什麼

§5.4 定義的是 **per-video 閘門**（單支 unverified > 5% → `needs_review`，
不進 `chunks.jsonl`）。§5.2 的表格卻把同一個 0.95 寫成「對象：**全部**」
的全域驗收門檻。

**同一個數字承載兩種語意。** 於是 R27 算出來的「四支合計 0.838」被當成
驗收依據，而那個數字混了四種成因。

| 拆開後 | |
|---|---|
| `PROVENANCE_PER_VIDEO_GATE = 0.95` | 真的擋。**值一個字都沒動** |
| `provenance_rate_overall` | 只記錄，列在 `thresholds.OBSERVED_ONLY` |

**這不是 §5.5 #7 禁止的調低門檻**——拿掉的是一個從來不該存在的全域門檻。

逐支量測帶**成因分解**寫進 `out/provenance.jsonl`。只給一個比率等於沒說：
R27 的 27 筆未通過裡，17 筆的病根不在內容品質。

## 3. 後果：`chunks.jsonl` 是空的

**四支全部被擋，產品輸出目前一個 chunk 都沒有。**

而 §7.4 的收尾定義是「產出真的被使用」。現在的狀態是：管線跑得完、
人工複核文件產得出來、但**知識庫拿不到任何東西**。

### 這個閘門其實是第二層

`build_chunks` 已經逐個 block 排除未通過的（`render.py`，會 log
「溯源為 X，已排除」）。也就是說**進到 `chunks.jsonl` 的每一個 chunk
本來就都是通過溯源的**。

per-video 閘門是疊在上面的第二層，語意是「這支影片的理解整體不可信，
連通過的部分也不要」。以 cxrqHABhWOU 為例：14 個 block 裡 13 個通過、
唯一那 1 個還是**歸屬標錯**（內容溯得到同段的另一個來源），
整支因此被丟掉。

### 為什麼我沒有動它

`docs/FROZEN.md` F2 寫得很明白：

> 0.95 從 §5.4 的「5% 容忍度」來，而**那個 5% 沒有依據**。
> 恢復觸發條件：當有了「產出好不好用」的評測（SPEC D-J），
> 若實測顯示某個溯源水準以下可用性明顯下降，**用那個實測值**訂門檻。
> 不是回頭撿 0.95。

在票 12 產出可用性證據之前，任何調整都是憑感覺換一個數字——
那正是 §5.2 對 `slide_text` CER 寫過的「不憑感覺訂一個數字」。

### 三個方向，留給使用者決定

1. **等票 12**。用可用性實測訂閘門。最正確，但收尾要多繞一圈。
2. **閘門改用「真的溯不到」的比例**，而不是全部未通過。
   實測：11/155 = **7.1%**，仍高於 5%，但 cxrqHABhWOU 會變成 0/14 = 0%
   而通過。**理由不是為了讓它變綠**——歸屬標錯的 block 已經被逐 block
   排除在 chunks 之外了，拿它去否決整支影片是重複計算同一個問題。
3. **接受現狀**，先讓票 08 的分段改動與票 10 的 prompt 重測降低未通過數，
   再看閘門會不會自然過。

**我沒有替使用者選。** 第 2 個方向看起來最合理，但它會改變一個
真的在擋東西的閘門的語意，那需要明確同意。

## 4. 護欄

- `OBSERVED_ONLY` 進了規約測試的白名單，`provenance_rate_overall`
  **不得**被誤登記成驗收門檻（`test_overall_rate_is_recorded_not_gated`）。
- `test_gate_is_per_video_not_overall`：一支很差不得拖垮另一支。
  這正是兩種語意合成一個數字時會發生的事——合計 0.70 看起來「沒過」，
  但實際上只有其中一支該被擋。
- `out/provenance.jsonl` 與 `chunks.jsonl`／`unverified.jsonl` 一樣，
  重跑同一支是**取代**不是累積。

## 5. 限制

- 四支影片、155 個 block，全部是中醫講經、全部手動字幕。
- `depends_on_correction` 實測為 0——不是機制沒用，是這批素材測不到
  （見 R28 §3）。
