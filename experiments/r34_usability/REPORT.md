# R34（票 12）：可用性指標——RAGAS 不用，檢索指標**目前分不出好壞**

2026-08-08。票 12 的第一步是**評估**，不是直接接上。評估完了，結論在下面。

---

## 1. RAGAS：不採用

**理由不是「裝不起來」，是它的三個指標全部要 LLM 當裁判。**

| RAGAS 指標 | 怎麼算 |
|---|---|
| Answer Relevance | LLM 從答案反推問題，比對與原問題的相似度 |
| Context Relevance | LLM 從 context 抽出「相關的句子」 |
| Faithfulness | LLM 把答案拆成主張，逐條對 context 檢查 |

在這個專案裡，那會是**用本地 LLM 去評判本地 LLM 的產出**——
正是票 01 剛修掉的「用來源 A 驗證來源 A」。

而且這不是理論顧慮。R21／R26 已經量過本地模型在這批中文素材上的表現：

- 投影片分類：同一個模型、同一批圖，光改 prompt 措辭就在 **0.636–1.000** 之間跳
- `slide_text` CER：**4.9%–37.8%**，視模型而定

拿一個這種穩定度的裁判去打分，量到的會是裁判的心情。

**FROZEN F4 的同一條紀律**：拿英文語料的結論套中文素材是推廣錯誤。
RAGAS 的門檻值（Video-RAC 報 0.87／0.82／0.91）也是英文素材上的，
就算接上去也不能拿那些數字當參照。

## 2. 改用檢索指標：完全機械化，沒有裁判

把使用者會問的問題向量化，看正確的 chunk 排第幾。
它回答的是**「我找不找得到我要的東西」**。

題組：`questions.json`，18 題，每題人工標出能回答它的 chunk。
判定標準是 §3.5 的自足要求——**讀那個 chunk 就答得出來，不必看別的**。

| | R@1 | R@3 | R@5 | MRR |
|---|---|---|---|---|
| weft chunk + `bge-m3` | **0.944** | 1.000 | 1.000 | **0.963** |
| weft chunk + `MiniLM` | 0.722 | 0.889 | 0.944 | 0.812 |

看起來很好。**但這個數字證明不了任何事**，見下。

## 3. 對照組揭穿了它：naive 切法幾乎一樣好

加一組**固定 200 字視窗**的 chunk——不做語意分段、不做理解、
不做溯源，就是把逐字稿切段：

| | chunk 數 | R@1 | R@3 | MRR |
|---|---|---|---|---|
| weft | 69 | 0.944 | 1.000 | 0.963 |
| **naive-200** | 40 | **0.889** | 0.944 | **0.919** |

**差距是 R@1 的 0.055——18 題裡的 1 題。**

也就是說：**這個指標目前分不出 weft 的產出與「什麼都不做」的差別**，
因此**不能當「夠好了」的訊號**。

### 為什麼分不出來

1. **語料太小。** 69 個 chunk、兩支影片。干擾項不夠多時，
   任何合理的表示法都能把關鍵詞對上。
2. **題目問的是「找得到嗎」，而 weft 加的價值不在那裡。**
   weft 相對 naive 多做的是**自足性**（chunk 是一個完整的想法）
   與**溯源**（這句話有出處）。檢索排名量不到這兩件事——
   一個被切成兩半的想法，只要含關鍵詞照樣排第一。
3. **題目是先讀 chunk 再出的。** 所以它們是「這批內容答得出來的問題」，
   不是「使用者會問的所有問題」。這量到的是檢索，不是涵蓋率。

## 4. 什麼樣的指標才分得出來——沒有實作，只提出

三個方向，都還沒做：

1. **自足性**：把檢索到的 chunk 單獨拿給人看，問「這段話單獨讀懂不懂、
   答不答得了那個問題」。naive 切法會在這裡失分，因為它從句子中間切開。
   **需要人工評分**，但不需要 LLM 當裁判。
2. **需要完整論證的問題**：「為什麼肝病很難治」要的是一整段推理
   （帳全錯 → 無從下手 → 只能早睡早起），naive 切法會把它切散。
   現有題組偏向事實查找，換一批題就能量到差別。
3. **擴大語料**：票 11 的 26 支課程 ≈ 800 個 chunk。干擾項多 10 倍之後
   R@1 才會有區辨空間。

## 5. 順帶量到的一個實質品質問題

讀 chunk 時發現產出裡混著簡體字與英文：

| | |
|---|---|
| 含簡體字的 chunk | **19/69 = 27.5%** |
| 簡體字佔全部字元 | 70/4813 = 1.45% |
| 含英文單字（≥3 字母）的 chunk | 6/69 = 8.7% |

例子：`小 intestine`、`幽门杆菌`、`恶搞`、`妈妈`。

**成因**：D24 只把 **ASR 輸出**轉繁（`s1a.asr_script_conversion`），
**S4c 生成的內容沒有經過任何字集正規化**。這四支用的是手動字幕
（本來就是繁體），所以簡體字**全部來自模型的生成**。

`小 intestine` 更明顯是翻譯殘留——模型在中文句子中間吐出英文詞。

**沒有現在就修**：這是 S4c 的產出問題，修法有兩條
（在 prompt 上要求、或在後處理轉繁），而後者會動到 §5.3 不變量 9
的邊界（`text_raw` 唯讀是對逐字稿說的，生成內容不在其列，但
「模型寫了什麼」與「我們改成什麼」需要留痕）。列為後續票。

## 6. 結論與門檻

**不訂門檻。** 票裡自己寫的：「不憑感覺訂門檻——首版只記錄，
累積足夠觀察後再談門檻（這正是 §5.2 對 CER 已經採用的紀律）」。

而且現在連「記錄什麼」都還沒定案——§3 證明現有的檢索指標
在這個規模下沒有區辨力。**先把它記在 `OBSERVED_ONLY` 都嫌早。**

`docs/FROZEN.md` F2 說 0.95 的恢復觸發條件是「當有了產出好不好用的評測」。
**那個評測還沒有。** 這張票把「RAGAS 不能用」與「檢索指標還不夠」
都量清楚了，但沒有交出一個能說「夠好了」的數字。

如實記錄，不假裝有。
